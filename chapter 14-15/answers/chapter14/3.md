# Chapter 14, Challenge 3: Memory Allocation

Two common open-source allocator designs are the allocators used by glibc and
jemalloc. They both keep metadata describing each allocated block, but their
strategies differ.

## How allocation works

An allocator receives a requested size, rounds it up for alignment, and finds a
free block large enough to hold it. If the block is larger than necessary, it
may split the remainder into another free block. If no suitable block exists,
the allocator requests more pages from the operating system.

## How freeing works

The allocator finds the metadata immediately before the user pointer. It marks
that block free and may merge it with adjacent free blocks. This merging is
called coalescing and helps prevent the heap from becoming needlessly
fragmented.

## Efficiency and fragmentation

Allocators use size classes, free lists, arenas, caching, alignment, and
coalescing to reduce overhead. Small allocations can be served from dedicated
size-class lists, while larger allocations may use page-level mappings. The
main fragmentation problems are:

- internal fragmentation: a block is larger than the requested object;
- external fragmentation: enough total free memory exists, but it is split into
  pieces that cannot satisfy one large request.

The allocator balances search speed, metadata overhead, locality, and wasted
space. A personal allocator using one large heap could use a header containing
`size`, `isFree`, and a pointer to the next block. Allocation would search for
a free block, split it when useful, and freeing would mark it available and
coalesce adjacent free blocks. The trade-off is that this simple first-fit
design is easier to understand but generally less sophisticated than production
allocators.
